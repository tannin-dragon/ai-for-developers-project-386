# AGENTS.md

Справка для работы с проектом **Callendar** — контракт бронирования звонков на TypeSpec/OpenAPI.

## О проекте

- Единый исходник контракта: `main.tsp` (TypeSpec 1.14). Эмиттер: `@typespec/openapi3`.
- Выход: `tsp-output/schema/openapi.yaml` (OpenAPI 3.1, в `.gitignore`).
- Сервис: `Callendar`, базовый путь `/v1`, сервер `http://app.loc:8080`.
- Две роли без регистрации: `Guest` (открытые эндпоинты) и `Owner` (заголовок `X-Owner-Key`, ошибка `401 INVALID_OWNER_KEY`).
- Документация по API и бизнес-правилам — в `@doc`-комментариях `main.tsp`.

## Команды (ОБЯЗАТЕЛЬНО)

На этой машине весь TLS-трафик перехватывает корпоративный MITM-прокси, поэтому Node.js должен
брать сертификаты из системного хранилища Windows. В каждой новой консоли выполнять:

```powershell
$env:NODE_OPTIONS="--use-system-ca"
npm install          # зависимостей
npx tsp compile .    # компиляция контракта
```

Успех компиляции: `Compilation completed successfully.` Проверка путей в OpenAPI: `Get-ChildItem tsp-output\schema`.

## Раздача приложения (Docker)

- `docker-compose.yml` и `nginx/default.conf` лежат уровнем выше (`../`), проект смонтирован в контейнеры как `/var/www`.
- Контейнер `app-nginx-1` (`8080→80`) отдаёт собранное SPA из `frontend/dist` на `http://app.loc:8080` с SPA-fallback на `index.html`; `/v1/*` → 404 (бэкенд не реализован; шаблон `proxy_pass` — в комментарии `nginx/default.conf`).
- После изменений фронта: `npm run build` в `frontend/` (dist смонтирован в контейнер, перезапуск не нужен). После правки `nginx/default.conf`: `docker exec app-nginx-1 nginx -t && docker exec app-nginx-1 nginx -s reload`.
- Dev-режим с HMR: `npm run dev` в `frontend/` (порт 5173, прокси `/v1` на `VITE_PROXY_TARGET`, дефолт `http://app.loc:8080`).
- phpinfo-заглушка `index.php` удалена; PHP-FPM (`app-php-1`) в раздаче не участвует, оставлен под будущий бэкенд.

## Подводные камни TypeSpec 1.14

- `@statusCode` ставится на **свойство** модели `@error`, а не на модель:
  `@error model X extends ProblemDetails { @statusCode statusCode: 409; }`.
- `@service(#{ title: "..." })` не принимает `version`.
- `@defaultValue` нет в стандартной библиотеке (есть `@minValue`/`@maxValue`); дефолты — в `@doc`.
- `@route("/v1")` на namespace задаёт префикс всех путей.
- Времена — `offsetDateTime`; ошибки — RFC 7807 `application/problem+json`; коды ошибок перечислены в `@doc`.

## Ключевые бизнес-правила (зафиксированы в контракте)

- Окно записи: `[сейчас, +14 дней)`.
- Рабочее время по умолчанию: Пн–Пт 09:00–18:00 (таймзона владельца из `WorkSchedule`).
- Шаг слотов: 15 или 30 минут (поле `slotStepMinutes` типа звонка).
- Активные бронирования не могут пересекаться по времени даже у разных типов звонков.
- Блокировки времени глобальны (`/v1/blocked-slots`); конфликт брони с блокировкой — `409 SLOT_BLOCKED`.
- `POST /v1/bookings` требует `Idempotency-Key`; повтор с тем же ключом/телом возвращает исходный ответ.

## Общие правила работы (из AGENTS_s3corp.md, без специфики того проекта)

### ABSOLUTE TRUTH PROTOCOL
- НЕ генерировать информацию, которую нельзя обосновать.
- Если уверенность < 95% — сказать «не знаю».
- Ответ всегда содержит одну из трёх частей: (1) чёткое решение, (2) конкретный запрос недостающих данных, (3) прямое признание невозможности решения.

### Правила честности и неопределённости
- **НЕ ПРИДУМЫВАЙ**: нет точного ответа/факта/данных — не изобретай, без обоснования никаких «вероятно/обычно делают так».
- **НЕ ДОМЫШЛЯЙ**: не заполняй пробелы в условии задачи; неполное условие — сказать об этом.
- **НЕ СОЧИНЯЙ**: никаких вымышленных примеров, ссылок, API, библиотек, данных.
- **Честное признание неудачи**: если задача не решается (мало данных, противоречия, техническая невозможность, нет знаний) — прямо написать: «Я не могу решить эту задачу, потому что [конкретная причина]».
- **Никаких отговорок**: «я бы сделал, но…» без чёткого решения = нарушение.

### Модель работы (для нетривиальных задач)
1. **Интервью** — проанализировать задачу, задать уточняющие вопросы.
2. **План** — цель изменения, затрагиваемые файлы, порядок действий, риски и предположения (показывается до реализации).
3. **Ограничить scope этапом** — большая задача делится на завершённые самостоятельные этапы.
4. **Минимальный инкремент** — только самое необходимое для задачи; «запасные» улучшения — отдельным пунктом в плане, не в коде.
5. **Верификация** — обязательна даже для очевидных правок: проверка результата конкретными сценариями.
6. **Отчёт** — по формату ниже.

### Принципы (Purpose)
- **Correctness** — изменение не ломает существующее; если поломка неизбежна — явно задокументировать и согласовать.
- **Maintainability** — код понятен другому через год: вложенность ≤3, без магических чисел и неявных зависимостей.
- **Explicit architecture** — новое поведение вписывается в существующие паттерны; новый паттерн — только с обоснованием.
- **Safe incremental delivery** — изменение разбивать на минимальные шаги, каждый проверять отдельно.
- **Business value per stage** — чётко сформулировать бизнес-задачу этапа; не добавлять «полезного», не относящегося к задаче.

### Ревью (Review expectations)
Обращать внимание на: несоответствие бизнес-требованиям, edge cases (пустые значения, NULL, лимиты), рискованные миграции (с явным планом отката), **contract drift** (изменение форматов между слоями без обновления документации), избыточную сложность, связанность и SRP.
Вывод ревью — три категории: **Критические** (блокируют), **Важные** (ближайший этап), **Опциональные**.

### Ожидаемый формат итогового ответа
1. **Summary** — ≤15 предложений, суть изменения и бизнес-ценность.
2. **Files/modules affected** — изменённые файлы с пояснением.
3. **Verification performed** — что именно проверяли (сценарии, данные, окружение), конкретные результаты.
4. **Known risks / tech debt / assumptions** — честно, включая предположения о данных/внешних системах.
5. **Manual QA steps** — пошаговая воспроизводимая инструкция.
6. **Recommended next step** — что дальше.
Без общих фраз «всё работает» — только конкретика.

### Если не уверены
Изучите ближайшие аналоги в коде → сформулируйте гипотезу → минимальный эксперимент (лог/вывод) → задайте уточняющий вопрос → задокументируйте неопределённость в плане и отчёте.

### Качество кода
- Читаемость и простота: вложенность ≤3 (ранние `return`/`continue`), константы вместо магических чисел, осмысленные имена.
- SRP: одна функция — одна задача; модули слабо связаны.
- Побочные эффекты: не менять глобальное состояние без необходимости; write-функции называть с глаголом (`save`, `update`, `delete`...).
- YAGNI: сначала конкретная задача, обобщение — при второй похожей.
- Следовать существующим конвенциям проекта и его формату кода.

### Инфраструктура и секреты
- Изменения инфраструктуры — как чувствительные к продакшену: порядок применения, способ отката, влияние на доступность.
- Секреты — только в защищённом хранилище (здесь: Windows Credential Manager), никогда не хардкодить и не коммитить.
- Для изменения в `.env`/конфигах — документировать и обновлять примеры.

### Документирование
- Любое новое поведение (изменение API, формата данных, маршрута, настройки) — отражать в документации/комментариях.
- Комментарии объясняют «почему», а не «что».
